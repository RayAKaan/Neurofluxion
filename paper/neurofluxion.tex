\title{Neurofluxion: An Interactive System for Exploring, Simulating, and Inspecting Neural-Network Computation}

\begin{abstract}
Neural-network software normally exposes a trained model through predictions, metrics, and layer structure, while detailed inspection of intermediate computation is often distributed across framework APIs, debugging instrumentation, and custom educational implementations. Neurofluxion is a full-stack interactive environment that connects model exploration, framework-backed execution tracing, and a separately implemented numerical simulator in one application. Its TensorFlow/Keras path executes selected models and exposes intermediate layer outputs together with bounded statistics and selected internal-detail views. Its NumPy simulator provides an independently constructed environment for building supported sequential networks, executing forward and backward passes, and inspecting parameters and gradients. A React interface connects these paths to architecture views, tensor inspection, mathematical expressions, training surfaces, and a pretrained-model registry. The two computational paths are deliberately treated as distinct: the simulator does not inherit registry checkpoints by implication, and framework trace values are not presented as simulator activations. We describe the architecture, interaction model, implementation contracts, and an evidence-driven validation protocol. Research validation includes fixed-configuration finite-difference graph oracles for Dense, Conv2D, RNN, LSTM, GRU, Embedding--Attention--RNN--Dense, and Conv2D--BatchNorm--Flatten--Dense graphs, together with one-batch parameter-update contracts for representative recurrent, convolutional/normalization, and embedding/attention/recurrent paths. A live OpenAlex/Crossref export on the frozen repository revision produced 2,400 raw records and 2,074 deduplicated candidates with zero query failures. These results establish bounded implementation evidence rather than universal numerical correctness, usability improvement, or model-performance superiority.
\end{abstract}

\begin{IEEEkeywords}
neural-network visualization, interactive machine learning, neural-network simulation, execution tracing, model inspection, reproducible software artifacts

\section{Introduction}
Deep neural networks are usually consumed through a compact interface: provide an input and observe a prediction. This abstraction is essential for deployment, but it hides the sequence of transformations that produces the output. Developers, researchers, and learners may instead need to inspect architecture, intermediate tensors, parameters, gradients, recurrent state, or the relationship between an individual operation and the values surrounding it. Existing visualization systems have demonstrated the value of interactive architecture and dataflow views, while machine-learning frameworks provide increasingly capable execution and instrumentation facilities \cite{wongsuphasawat2018,deepeyes2018,net2vis2021}.

Neurofluxion addresses a related implementation problem: how to connect executable neural-network state with a user-directed inspection workflow while retaining an independently inspectable numerical environment. The application therefore contains two computational paths. The first is a TensorFlow/Keras path for framework-backed model execution and intermediate-output tracing. The second is a NumPy simulator in which a user constructs a supported network and can inspect its forward and backward computations. The frontend connects these paths to architecture, tensor, mathematical, and training views.

The distinction between the paths is central to the system design. A Keras trace is produced from a selected Keras model and its runtime outputs. A simulator trace is produced by the separate NumPy implementation. The existence of an identically named layer or operation in both paths does not establish shared weights, shared state, or numerical equivalence. This separation prevents the interface from implying evidence that the implementation does not provide.

The work is an artifact-centered implementation/system paper rather than a new-learning-algorithm paper. Its contributions are:
\begin{itemize}[leftmargin=*]
  \item an integrated full-stack environment that couples framework-backed model exploration with a separately implemented, inspectable numerical simulator;
  \item a construction-to-execution-to-inspection workflow spanning supported forward/backward computation, parameter and gradient inspection, model metadata, and selected internal values;
  \item an explicit characterization of framework trace semantics, including bounded tensor payloads and cumulative-subgraph timing attribution;
  \item a reproducible research-validation layer containing operation-level finite-difference graph oracles, one-batch training-update contracts, browser provenance tests, and literature-search artifacts;
  \item an evidence ledger and scope discipline that separates source-confirmed behavior, independently verified results, bounded claims, and unresolved implementation limitations.
\end{itemize}

The paper does not claim universal support for arbitrary neural-network graphs, equivalence with optimized framework kernels, improved learning outcomes, or superiority over existing visualization systems. Such claims require evidence beyond the present implementation study.

\section{Related Work}
Interactive neural-network visualization has a long history of exposing model structure and intermediate behavior. The TensorFlow Graph Visualizer applies graph transformations and hierarchical interaction to make large dataflow graphs more legible and supports exploration of nested model structure \cite{wongsuphasawat2018}. DeepEyes instead emphasizes progressive visual analytics for network design and training, supporting analysis of layers and learned patterns during iterative model development \cite{deepeyes2018}. Net2Vis introduces a visual grammar for automatically generating publication-oriented CNN architecture diagrams \cite{net2vis2021}. These systems establish important precedents for interactive model structure and visual analysis.

Neurofluxion differs in emphasis rather than claiming priority. Its simulator is an executable numerical environment, not only a visualization of an already defined framework graph. Its framework-backed trace path and simulator path are presented side by side but remain computationally separate. The resulting workflow is organized around selecting or constructing a model, executing it, selecting an execution stage, and inspecting the values associated with that stage.

More recent work such as Graph of Trace demonstrates the value of exposing fine-grained execution events as interactive traces for inspection of complex AI-agent workflows \cite{gao2026}. Neurofluxion applies a related trace-oriented interaction principle to neural-network computation, but its trace semantics are constrained by the values actually returned by its Keras execution service and by its separately implemented simulator. The present work therefore treats trace visualization as an interaction mechanism rather than evidence of general interpretability.

TensorFlow provides the framework-backed computational foundation for the application \cite{abadi2016}, while NumPy provides the array-programming substrate used by the independent simulator \cite{harris2020}. Keras is used as the model-level API in the framework path \cite{chollet2015}.

\section{System Architecture}
Neurofluxion is implemented as a React/Vite/TypeScript client and a FastAPI/Python backend. The repository identifies React 18, Vite, Tailwind CSS, Zustand, FastAPI, Uvicorn, WebSockets, TensorFlow/Keras, NumPy, Three.js, Recharts, and KaTeX as the principal technology components. The client contains dedicated surfaces for prediction, models, Lab execution, training, and simulator interaction.

\subsection{Framework-backed model path}
Prediction Mode uses a central model registry with model-family metadata, lazy loading, caching, preprocessing information, and provenance records. The repository documents MNIST multilayer perceptrons, ImageNet CNNs including MobileNetV3-Small, MobileNetV2, ResNet50, and VGG16, and an IMDB sentiment BiLSTM. Registry models are downloaded lazily rather than bundled into the repository. Unavailable checkpoints are represented as unavailable rather than substituted with fabricated models.

The Lab execution path is separate from the registry catalog. Its trace service constructs a multi-output Keras model over non-input layers and evaluates it on a prepared input. Stage records include layer identity and type, operation metadata, activation information, shapes, parameter counts, timing fields, and output statistics. Some payloads are bounded before serialization and carry a sampling indicator. Consequently, a trace record must not be interpreted as a complete tensor unless its provenance and sampling state support that interpretation.

\subsection{NumPy simulator path}
The simulator contains a graph builder, forward engine, backward engine, layer implementations, optimization/training components, and session-related state. The audited graph builder constructs a validated sequential composition of supported layer objects and propagates shapes through the configured sequence. Observed dispatch includes dense/output, batch normalization, Conv2D, max/average pooling, flatten, vanilla RNN, LSTM, GRU, embedding, attention, and residual-related layers.

The builder maintains layer instances, parameter-bearing layer mappings, activation/pre-activation collections, parameter and FLOP totals, and an architecture identifier. The architecture identifier is derived from the sequence of layer neuron counts and is therefore not a complete serialization of every configuration option. The simulator is consequently described as a validated sequential construction path rather than as an arbitrary-edge directed acyclic graph.

\subsection{Interaction lifecycle}
The principal interaction is
\begin{equation*}
\textit{construct or select}\rightarrow\textit{execute}\rightarrow\textit{capture}\rightarrow\textit{select}\rightarrow\textit{inspect}.
\end{equation*}
In Simulator Mode, construction precedes execution. In the Lab, a Keras model and input are selected before tracing. The frontend then presents the available execution state through stage, formula, tensor, architecture, and model-detail views.

\section{Inspectable Simulator}
\label{sec:simulator}
The simulator is designed around explicit numerical computation rather than merely displaying a framework graph. For a configured sequence of supported layers, the high-level forward relation is
\begin{equation}
 h^{(0)}=x,\qquad h^{(\ell)}=f_{\ell}\!\left(h^{(\ell-1)};\theta_{\ell}\right),
\end{equation}
where $x$ is the supplied input, $f_\ell$ is the implemented operation, and $\theta_\ell$ denotes the parameters associated with that layer.

For dense computation, the implementation exposes a finer-grained forward trace. The conceptual neuron computation is
\begin{equation}
 z_j^{(\ell)}=\sum_i w_{ji}^{(\ell)}h_i^{(\ell-1)}+b_j^{(\ell)},\qquad
 h_j^{(\ell)}=\phi_\ell(z_j^{(\ell)}).
\end{equation}
Dense-only forward traces expose matrix multiplication, bias addition, and activation records. Mixed/non-dense graphs instead expose a generic forward record per instantiated layer. This difference is an implementation property of the current trace engine and is important when interpreting step counts.

The simulator's forward-step API regenerates the full forward sequence and then selects the requested step. It is therefore step-indexed replay/inspection, not incremental execution. The same property applies to backward-step selection: the full backward computation is performed before the selected step is returned.

\subsection{Backward computation}
The dense-only backward path computes a loss, traverses dense layers in reverse order, derives layer deltas, forms weight gradients from outer products, and forms bias gradients from the corresponding delta. The generic path initializes an output gradient and invokes each instantiated layer's backward method in reverse order. Because these branches have different contracts, the manuscript does not collapse them into a universal backpropagation claim.

A particularly important validation boundary is the loss/activation relationship. The audited dense-only implementation treats MSE differently from other configured loss names when forming the final delta. The paper therefore reports numerical validation only for fixed tested configurations rather than asserting correctness for arbitrary activation/loss combinations.

\section{Framework Execution Trace}
The Keras trace service creates an activation model containing the non-input outputs of the selected Keras model and executes it to collect intermediate values. Each stage includes structural metadata and output statistics. For convolutional and pooling outputs, feature maps are rearranged for visualization; some output payloads are bounded before JSON serialization.

Timing is deliberately described with precision. The service measures cumulative prefix executions and derives a stage-level timing value from successive cumulative measurements. If $T_k$ is the measured time for a model prefix through stage $k$, the reported attribution is conceptually
\begin{equation}
 \widehat{t}_k=T_k-T_{k-1}.
\end{equation}
This is not an isolated hardware-kernel measurement. It includes framework scheduling, repeated prediction overhead, and measurement noise. It is therefore useful as an execution-attribution field for the interactive trace, not as a substitute for a profiler.

The trace also records model trained/untrained state and an execution timestamp. These fields provide useful provenance but do not by themselves establish reproducibility of a model checkpoint; checkpoint identity, preprocessing, environment, and input must also be retained.

\subsection{Detailed inspection}
The trace service includes dedicated paths for dense-neuron detail, convolution-cell detail, and LSTM gate/state detail. Such views are architecture-specific. A dense-unit inspection can expose the relationship among incoming activations, weights, bias, pre-activation, and activation. A convolution-cell view requires spatial and channel indexing. An LSTM view requires timestep and gate/state semantics. The manuscript therefore treats these endpoints as implementation-specific inspection facilities rather than as generic explanation algorithms.

\section{Frontend Workflow}
The frontend provides architecture construction and visualization, execution controls, tensor inspection, mathematical expressions, model metadata, training surfaces, and prediction interfaces. The Simulator surface exposes controls for layer construction, activation selection, optimization, datasets, forward/backward execution, and parameter/gradient inspection. The Lab surface provides framework-backed execution and trace inspection.

The frontend is not presented as a generic explainability layer. Its purpose is to expose the executable state already produced by the selected computational path. This distinction is particularly important for values that are sampled, bounded, estimated, or derived.

The current research validation also contains adversarial browser tests for two provenance invariants: stale inspection state after graph replacement and out-of-order responses. These tests currently reproduce known defects and remain expected failures until the application runtime is explicitly authorized for modification and the invariants are satisfied. The paper consequently does not claim perfect UI provenance under asynchronous graph switching.

\section{Validation Methodology}
The validation strategy is operation-level and reproducibility-oriented. It is not a benchmark of model accuracy or a user study.

\subsection{Numerical graph oracles}
Finite-difference graph checks compare selected analytical gradients against independently computed central finite differences for fixed small configurations. The merged research suite covers:
\begin{itemize}[leftmargin=*]
\item Dense and Conv2D graph configurations;
\item vanilla RNN configurations;
\item LSTM configurations;
\item GRU configurations;
\item Embedding--single-head Attention--RNN--Dense composition; and
\item Conv2D--BatchNorm--Flatten--Dense composition.
\end{itemize}
Each oracle is bounded to its declared graph, input, objective, data type, random seed, perturbation and tolerance. A passing result is evidence for that tested configuration only; it is not evidence for every tensor shape, loss, optimizer, or layer composition.

\subsection{Training-update contracts}
One-batch parameter-update contracts independently exercise representative optimizer paths for LSTM/GRU, Conv2D/BatchNorm, and Embedding/Attention/RNN/Dense configurations. These contracts verify the expected parameter-update behavior of the fixed test batches. They do not establish convergence, generalization, or broad gradient correctness.

\subsection{Reproducibility and source freeze}
The current repository main revision used for this manuscript implementation is \texttt{50de1fb7328d82c8f4799bbf3feffff8fd713216}. The live literature export ran on that exact revision in GitHub Actions on Ubuntu 24.04.5 with CPython 3.11.17. The exporter completed 12 successful queries with zero query failures, zero partial failures, and zero failed queries; it produced 2,400 raw records and 2,074 deduplicated records. The resulting artifact is GitHub Actions artifact 12153262023 from workflow run 39172931277.

The literature stage is therefore reproducible as a metadata export, but it is not described as a completed systematic review. Human screening, full-text extraction, duplicate adjudication beyond automated deduplication, and citation snowballing are separate review activities and are not inferred from the export counts.

\section{Implementation Evidence and Reproducibility Record}
The source repository provides a Python backend test command, frontend lint/build commands, and dedicated research workflows. The evidence ledger records the exact workflow families used for the recent graph-oracle and training-contract validation. The paper treats a repository test definition as insufficient evidence by itself; claims of successful validation are tied to recorded workflow outcomes.

The implementation record also preserves an important separation among three execution/training channels. The \texttt{/stream} WebSocket is a synthetic topology-and-metrics demonstration generated from hard-coded identifiers, weights, perturbations, and formula-derived curves; it is not live model execution. The \texttt{/train} channel delegates to the framework training manager, while simulator training uses a separate simulator session/training path. These channels must not be described as a single shared training state.

For framework-backed model demonstrations, reproducibility additionally depends on the model registry's checkpoint provenance, preprocessing, cache state, and device. For simulator demonstrations, reproducibility depends on the graph specification, input, parameters, objective, random seed, dtype, and execution path. The paper therefore recommends reporting these fields alongside any future quantitative figure.

\section{Discussion}
The principal design choice in Neurofluxion is to make computation inspectable without pretending that every visualization has the same provenance. Framework-backed traces are valuable because they expose real intermediate outputs from a selected Keras model. The independent simulator is valuable because it exposes a more explicit numerical execution model and allows a user to construct small configurations whose behavior can be validated independently.

This dual-path design creates an engineering cost: every operation that appears in both environments has potentially different semantics, supported shapes, parameter representations, and numerical behavior. The evidence ledger and graph-level oracles address this cost by requiring operation-specific validation instead of relying on visual similarity.

The same principle applies to performance and timing. A per-stage timing number is useful in an interactive trace, but the current implementation derives it from repeated cumulative-prefix execution. Reporting it as a kernel benchmark would overstate what the measurement means. Similarly, a bounded tensor visualization is useful for interaction but is not a complete tensor dump. The system's inspection contract is therefore best understood as provenance-aware interactive instrumentation.

\section{Limitations}
Several limitations bound the claims of this paper.

First, the simulator is not an arbitrary graph execution engine in the evidence currently audited. Its principal builder constructs a validated sequential composition, and the architecture identifier is a compact neuron-count sequence rather than a complete graph serialization.

Second, numerical evidence is selective. The finite-difference and training-update suites cover representative fixed configurations, but they do not establish correctness for every supported shape, activation, loss, optimizer, or composition. In particular, loss/activation compatibility and some generic backward summaries remain implementation-specific validation concerns.

Third, the framework trace is not a hardware profiler. Its timing values are cumulative-subgraph differences and can contain framework overhead and measurement noise. Serialized outputs may also be bounded or sampled.

Fourth, the current browser provenance suite exposes known stale-response and graph-switch defects. These tests are deliberately retained as expected failures so that the defects remain visible rather than being silently converted into green tests. No runtime fix is claimed in this paper because application-source modification is outside the current research-only implementation scope.

Fifth, the literature search is a reproducible metadata export, not a completed systematic review. The current manuscript therefore avoids claims of comprehensive coverage, priority, or novelty based solely on search counts.

Finally, the work contains no controlled human-subject evaluation. It cannot establish that Neurofluxion improves learning outcomes, usability, debugging efficiency, or educational effectiveness.

\section{Conclusion}
Neurofluxion is an interactive full-stack environment for exploring neural-network computation through two deliberately separated execution paths: a TensorFlow/Keras path for framework-backed model execution and trace capture, and a NumPy path for independently constructed numerical simulation. The frontend connects these paths to architecture, tensor, mathematical, model, and training views while retaining value provenance.

The implementation evidence supports a bounded system contribution. Recent research validation provides fixed graph-level finite-difference checks across dense, convolutional, recurrent, attention, embedding, and normalization compositions, together with one-batch training-update contracts. A live literature export is reproducible at the current source revision. These results are sufficient to document the implementation and its validated slices, but not to claim universal simulator correctness, superior visualization, or improved human outcomes.

The central methodological lesson is that an interactive neural-network inspection system should expose not only values but also the computational path that produced them. Neurofluxion's separation of framework traces, simulator traces, synthetic demonstration streams, and research-validation artifacts provides a concrete implementation of that provenance-aware principle.
